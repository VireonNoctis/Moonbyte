# Moonbyte Game Runtime — first playable slice

- Status: Implemented in-process domain and Discord adapter slice.
- Persistence: Not implemented; sessions reset when the process restarts.
- Authority: Rust owns game rules, participants, phases, turn order and outcomes.

This document describes the code that currently exists. It is intentionally narrower than the World Loom product specification.

## Current game modules

| Stable ID | Mode | Rules currently implemented |
| --- | --- | --- |
| tic-tac-toe | Two players | 3×3 board, legal placement, occupied-cell rejection, turn order, horizontal/vertical/diagonal wins and draw detection. |
| connect-four | Two players | Seven columns, six rows, gravity-based placement, full-column rejection, four-direction win detection and draw detection. |
| memory-match | Solo | Eight positions, four fixed pairs, duplicate/matched-position rejection and completion after all pairs are found. |
| word-scramble | Solo | One original five-letter starter puzzle, case-insensitive answer checking and three bounded attempts. |

Memory Match currently uses a fixed starter arrangement so the first implementation does not imply an unverified random shuffle. Word Scramble currently contains one starter puzzle. Neither limitation should be described as a complete production content catalogue.

## Session lifecycle

The runtime supports:

1. Start: a solo game enters Active; a two-player game enters WaitingForPlayers.
2. Join: the first distinct player from the same guild fills the two-player lobby.
3. Act: every mutation validates the session phase, guild scope, participant membership, turn owner, action range and game-specific legal move.
4. Complete: game rules produce a winner, draw or completed solo result.
5. Leave: any participant may end an unfinished session.
6. Read: only a participant in the matching guild context can inspect the snapshot.

Session IDs are generated by a monotonic process-local counter. They are convenient references, not durable IDs or security credentials. The runtime is intentionally single-process and in-memory. A restart loses every active session. Do not advertise reconnect recovery, saved progress or cross-instance coordination.

## Ownership boundaries

- The game engine contains pure rule transitions and does not import Serenity or Poise.
- The runtime owns the short-lived session registry and calls the engine.
- The command layer converts Discord identity and guild context to the runtime contract.
- The frontend, when introduced, must submit intent to Rust and must never calculate trusted outcomes or ownership.
- No game state is written directly by a command handler.

The registry currently uses a short synchronous mutex-protected map. Its critical sections contain only in-memory lookups and state transitions; no await, Discord HTTP request or disk I/O occurs while the lock is held. This is suitable only for the current small runtime and must be revisited alongside persistence and measured concurrency.

## Error and abuse handling

The runtime rejects unknown games, malformed or out-of-range actions, occupied cells, full columns, already-matched positions, repeated positions, wrong turns, non-members, incorrect guild context, non-joinable lobbies and actions after a session ends.

A rejected action does not advance the game state or action count. The runtime does not accept client-supplied winner, score, balance or completion fields.

## Tests

The domain tests cover parser bounds, tic-tac-toe win detection, occupied-cell rejection, Connect Four vertical completion, Memory Match pair completion and Word Scramble attempt/answer behavior. Runtime tests cover session IDs, guild-scoped lobby joins, DM multiplayer rejection, private session reads, participant checks, turn ownership, duplicate moves, leave behavior and completed-session rejection.

These are unit tests for the pure Rust domain and in-process runtime. They are not a Discord live-guild smoke test, database integration test or persistence/recovery test.

## Known gaps before the next release gate

- SQLite connection, migrations, repositories and versioned session snapshots.
- Durable player identity, profiles, results and progress.
- Reconnect/restart recovery and expiry/cleanup policy.
- Expiring session IDs and stronger unguessable external references where public exposure requires them.
- Discord button/select interactions and message edits for board updates; current input uses commands.
- A deterministic content registry and multiple reviewed Memory Match / Word Scramble puzzles.
- Privacy data inventory, export, confirmed deletion and retention jobs.
- Structured logging, graceful shutdown and service health reporting.
- A visual library and Discord Activity using Next.js, React, TypeScript and the official Embedded App SDK.

Do not mark these items complete until code, integration tests and operational documentation prove them.
